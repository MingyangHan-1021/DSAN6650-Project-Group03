# 阶段 1：基线（随机 + 规则策略）

对应文档里的"阶段 1：基线"。两个基线一条命令跑完三档难度 × 20 个种子，结果写入
`results/csv/`，另有一条命令给出环境的**理论产能**，用来判断三档难度是否合理。

```bash
# 两个基线一起跑，20 种子 × easy / medium / hard
python scripts/baselines.py --policy both \
    --config configs/env/easy.yaml configs/env/medium.yaml configs/env/hard.yaml --seeds 0-19

# 环境的理论产能 vs 各档需求
python scripts/capacity.py --config configs/env/easy.yaml configs/env/medium.yaml configs/env/hard.yaml
```

产出：

| 文件 | 内容 |
|---|---|
| `results/csv/baselines_random.csv` | 每个种子的完整指标（34 列） |
| `results/csv/baselines_rule.csv` | 同上 |
| `results/csv/baselines_summary.csv` | 长表：config / policy / metric / mean / std |

评测种子统一 0–19；规则策略完全确定性（同种子两次跑结果相同，`tests/test_baselines.py` 有测试盯着）。

## 两个策略

**random**（`--policy random`）：每步从合法动作里均匀随机选，只当下界用。

**rule**（`--policy rule`）：手写的菜谱任务链调度器，不是打分器。一道菜拆成站点访问链，
两个智能体从共享任务池领活。它有两种装盘模式：

* **停盘模式**（open 厨房里不需要灶台的菜：沙拉、汉堡）——先把空盘停在柜台，备料的人
  `取货 → 切/煎 → 直接把料放到那个盘子上`，最后一个完成的人取盘出餐。
  一盘菜只占 1 个柜台，而且省掉"放到柜台、之后再走回来取"的往返。
* **手盘模式**（需要灶台的菜：汤、意面、披萨）——盘子必须跟着人去锅/烤箱取菜，
  所以配料先备在柜台上，装盘的人一路走一路加。

其他规则：

- 同时最多推进 2 道菜（按 deadline；试过 3、4，更差——柜台是瓶颈）
- 有一道"要灶台"的菜在跑时，第二道优先挑不需要灶台的菜，避免两个人盯着锅等
- 灶台按 plan 分配（一碗汤的两个番茄进同一口锅）；锅快好了（剩余 ≤4 步）就提前拿盘过去等，
  因为"发现好了 → 回盘子架 → 再去锅边"通常超过 8 步的烧糊窗口
- split 厨房里一条链跨两个区域，会在柜台处切成两段交给不同的人（助手做到柜台、厨师接手）
- 每个动作执行完**先校验后置条件再推进**（拿货真的拿到了吗？料真的进盘了吗？），
  失败就从料箱重来或把手里的东西放到柜台；一条任务等柜台/灶台超过 14 步就放弃整条 plan

`--solo` 把所有活交给智能体 0，用来衡量协作带来的收益。

## 结果（seeds 0–19，均值 ± 标准差）

| 难度 | 策略 | 完成订单 | 到达订单 | 需求菜品 | 出菜 | 收入 | 小费率 |
|---|---|---|---|---|---|---|---|
| easy | random | 0.00 ± 0.00 | 7.20 | 8.60 | 0.00 | 0.0 | 0.000 |
| easy | rule | 3.65 ± 2.15 | 7.20 | 8.60 | 4.75 | 70.7 | 0.174 |
| medium | random | 0.10 ± 0.30 | 13.45 | 17.55 | 0.15 | 2.3 | 0.009 |
| medium | rule | 5.10 ± 1.61 | 13.45 | 17.55 | 7.25 | 114.9 | 0.128 |
| hard | random | 0.00 ± 0.00 | 18.20 | 29.20 | 0.00 | 0.0 | 0.000 |
| hard | rule | 1.40 ± 1.50 | 18.20 | 29.20 | 3.00 | 43.6 | 0.072 |

其他指标（medium / rule）：平均完成时间 54.8 步、浪费 0.15、烧糊 0.35、handoff 3.5、
没有干净盘子 1.4 步、两个智能体空闲 104 / 157 步（共 600 步的 44%）。

- 随机策略三档都约 0 单 → 环境不能被瞎蒙解开，下界有效。
- 规则策略 medium 出 7.25 盘、easy 最好一局 8 盘、hard 也能稳定出菜 →
  "环境在合理配合下做得出菜"成立。
- **单人参照（medium）**：`--solo` 3.00 单 / 4.50 盘，双人 5.10 / 7.25 → 协作约 1.6 倍。

## 难度校准：用理论产能给出结论

`scripts/capacity.py` 按菜谱和布局算一盘菜的**下界**：理想计划需要的站点访问、
按布局算的走路时间、两人里更快的那个技能、没有争抢、锅里在煮的时候人可以干别的。
真实策略只会更慢，所以

```
每盘的实际步数  >=  (每盘的 agent-steps) / 智能体数
```

跑出来：

| 难度 | 每盘 agent-steps | 两人并行折合 | 300 步产能 | 需求 | 需求/产能 | 判定 |
|---|---|---|---|---|---|---|
| easy | 33.0 | 16.5 步/盘 | 18.2 盘 | 8.6 盘 | 47% | 宽松 |
| medium | 33.8 | 16.9 步/盘 | 17.8 盘 | 17.6 盘 | **99%** | 卡在理论上限 |
| hard | 35.4 | 17.7 步/盘 | 16.9 盘 | 29.2 盘 | **172%** | 必然过载 |

这正好解释了 README 里"两人 15–18 步做出一个菜"的说法：它等于理论下界本身。
所以三档的设计意图是自洽的：

- **easy 有 2 倍余量**，适合当"能学会"的档；
- **medium 的需求≈产能**，只有接近最优的策略才能跟上——任何低效都会直接变成过期订单；
- **hard 的需求是产能的 1.7 倍**，注定有大量订单流失（设计如此）。

规则策略现在 medium 是 **41 步/盘**（300/7.25），是理论下界的 2.4 倍，所以只完成 41% 的需求。
换句话说：**medium 不是"太难"，而是"按最优策略设计"**；它会把策略的效率差距放大成完成率。
阶段 2 的 RL 结果应该拿 16.9 步/盘作为参照上限，而不是拿 0 单当参照。

### 敏感性实验（medium，20 种子）

| 设置 | 完成订单 | 出菜 |
|---|---|---|
| 基线 | 5.10 | 7.25 |
| 到达率 ×0.7 | 4.55 | 6.15 |
| `burn_after` 8 → 12 | 5.10 | 7.15 |
| 耐心 100–140 → 130–170 | 5.10 | 7.30 |

```bash
python scripts/baselines.py --policy rule --config configs/env/medium.yaml --seeds 0-19 --arrival-scale 0.7
python scripts/baselines.py --policy rule --config configs/env/medium.yaml --seeds 0-19 --override burn_after=12
python scripts/baselines.py --policy rule --config configs/env/medium.yaml --seeds 0-19 \
    --override orders.patience_min=130 --override orders.patience_max=170
```

放宽耐心、放宽烧糊窗口对完成量没有影响；需求降 30% 时出菜降 15%、完成率从 38% 升到 48%。
这符合"产能受限"的判断：难度参数（耐心/烧糊）不是瓶颈，**每盘菜的效率**才是。

## 下一步

1. 规则策略 41 步/盘 → 理论下界 16.9 步/盘，还有约 2.4 倍空间（空闲 44%、停盘/手盘各一半）。
   继续压的话优先看：闲置的智能体去提前备料（柜台只有 3 个，要注意别把柜台堵死）、
   把手盘模式也改成"停盘 + 取盘"，以及减少 plan 切换时的空档。
2. 阶段 2 的 MaskablePPO / Double DQN 可以直接用这份 CSV 的格式和种子约定，
   把 16.9 步/盘（≈17.8 盘）当作理论上限画在图上。

## 已知局限

- 规则策略是**下界参照**，不是上限；它没有搜索也没有学习。
- `--solo` 只在 open 厨房有意义；split 厨房里一个人做不完一道菜，不能直接比较。
- 停盘模式让 open 厨房的 handoff 变少（1.7/3.5 次），这是策略选择，不是环境变了。
- 随机策略每局浪费 26–46 个食材，是随机动作的正常表现，不是 bug。
- 产能下界忽略了争抢与等待（所以是下界），也没有考虑订单的到达节奏。
